# JAO Business Rules and Gaps

**Documentation date:** 2026-10-28. **Source revision:** `9cb1a64af7f6342b9a5dde13a00d5a9bf608a452` plus pre-existing working-tree changes. **Implemented** means visible in source, not runtime-tested. **Intended** comes from the owner; **gap** identifies an incomplete or inconsistent source path. Follow [security guardrails](../security-guardrails/SECURITY_POLICY.md) before proposing a fix.

## Invitations and applicant access

| Rule | Source status and evidence | Required review |
| --- | --- | --- |
| Generate an unpredictable invitation and store only its hash. | **Implemented in source:** `Str::random(64)` and SHA-256 storage (`app/Http/Controllers/ApplicationInvitationController.php`). The queued delivery job implements `ShouldBeEncrypted` (`app/Jobs/SendApplicantInvitation.php`). | Raw token is needed for the applicant link; queue encryption and delivery were not runtime-tested. |
| Enforce expiration. | **Partial:** seven-day expiration is set at creation (`app/Http/Controllers/ApplicationInvitationController.php:22`); form and submission queries check `expired_at` (`app/Http/Controllers/ApplicationFormController.php:19-24`; `app/Http/Controllers/ApplicationSubmissionController.php:35-39`). | Migration defines `expired_at` as `date` (`database/migrations/2026_08_27_094451_create_application_invitations_table.php:21`) while queries compare with `now()`; confirm exact intended end-of-day semantics without database access in this task. |
| Enforce single-use submission. | **Partial:** submission locks the invitation row, requires `used_at` null, and sets it inside a transaction (`app/Http/Controllers/ApplicationSubmissionController.php:35-62`). Form retrieval now rejects used invitations (`app/Http/Controllers/ApplicationFormController.php:19-25`). | Migration source has no unique constraint on `applications.application_invitation_id` (`database/migrations/2026_08_28_024347_create_applications_table.php:17-29`). Review replay behavior and database invariant under concurrency. |
| Validate an invitation token without leaking its value. | **Partial:** public form retrieval hashes the token and checks expiry and unused state (`app/Http/Controllers/ApplicationFormController.php:19-32`). There is no separate validation route; the unrouted `checkToken()` method was removed. `ValidateApplicationInvitation` remains an unused alias that compares the raw token to the stored hash (`bootstrap/app.php:19-22`; `app/Http/Middleware/ValidateApplicationInvitation.php:20-29`). | Keep token values out of logs and cache keys. Do not attach the unused middleware without correcting its hash lookup. |

## Forms, answers, and submission

| Rule | Source status and evidence | Required review |
| --- | --- | --- |
| Serve only a published version assigned to the invitation's job. | **Partial:** form retrieval filters `status = published` and job assignment, then takes the first match or rejects missing forms (`app/Http/Controllers/ApplicationFormController.php:27-38`). Invitation creation also requires a published job with an assigned published form (`app/Http/Controllers/ApplicationInvitationController.php`). | Multiple assigned published versions have no explicit selection rule; the invitation does not pin a version. Assignment request checks only UUID existence (`app/Http/Requests/CreateJobFormVersionAssignment.php:28-30`), not publication status. |
| Keep version numbering and publication state consistent. | **Partial:** creation locks the template, increments its latest version, and sets `published_at` only for `published` (`app/Http/Controllers/FormVersionController.php:36-54`). | Create/update requests accept arbitrary status text (`app/Http/Requests/CreateFormVersionRequest.php:25-27`; `app/Http/Requests/UpdateFormVersionRequest.php:25-28`). Migration source makes `version` globally unique (`database/migrations/2026_08_27_084606_create_form_versions_table.php:19`), while controller numbering is per template. Actual schema was not checked. |
| Accept only fields belonging to the selected form version and validate answer types/required values. | **Gap:** request validates UUID existence and nullable answers, but no ownership or per-field checks (`app/Http/Requests/CreateApplicationAnswerRequest.php:29-40`). Fields store `is_required` and `validation_rules` (`app/Models/FormField.php:15-32`). | Define field ownership, allowed options, types, required answers, payload size, and duplicate-field behavior at the submission boundary. |
| Submit all answers atomically with exactly one application. | **Gap:** transaction and row lock are present, but the answer list starts empty and is mapped from that empty list, so submitted answers are not inserted (`app/Http/Controllers/ApplicationSubmissionController.php:35-62`). | Use validated answers and enforce invitation/job/version consistency, duplicate prevention, and a database uniqueness strategy with separately approved schema work if needed. |
| Preserve applicant privacy. | **Review needed:** form retrieval adds invitation email to its response (`app/Http/Controllers/ApplicationFormController.php:33`); `ApplicationInvitationResource` uses default model serialization if invoked (`app/Http/Resources/ApplicationInvitationResource.php:15-18`). | Minimize applicant fields and never expose a token hash or raw token in a public resource. No live response was inspected. |

## Job listings and onboarding

- **Owner intent:** public job listings should show only publishable public data. **Current source:** job index is API-key gated and filters only an optional department, with no published-state filter (`routes/api.php:20-27`; `app/Http/Controllers/JobHiringController.php:17-24`). Do not reuse it as a public listing without a scoped security review.
- **Owner intent:** applicants can access authorized onboarding forms and submit onboarding information. **Current source:** onboarding models and migrations exist, but `app/Http/Controllers/OnboardingController.php:13-47` and `app/Http/Controllers/OnboardingInvitationController.php:13-47` are empty scaffolds and no onboarding route is declared in `routes/api.php`. Invitation expiration, single use, field ownership, and submission rules remain **planned/unknown**.
- **Data integrity review:** `ApplicationInvitation::application()` declares `BelongsTo` (`app/Models/ApplicationInvitation.php:23-26`), while the application table contains the invitation foreign key (`database/migrations/2026_08_28_024347_create_applications_table.php:20`). Confirm the intended inverse relation before relying on it.

These are documentation findings, not authorization to change application source or migrations. Review [architecture](ARCHITECTURE.md) and [API boundaries](API_BOUNDARIES.md) when planning any implementation.
